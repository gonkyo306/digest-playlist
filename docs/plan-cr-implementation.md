## この計画の考え方
- 今回のCR-001〜CR-008は、**「検索画面をメドレーから独立させる」（CR-006）**と**「再生をメドレー詳細画面のライフサイクルから切り離す」（CR-003）**という、既存実装の前提を変える2つの構造変更を土台にしています。他のCR（検索方式の拡張、無限スクロール、アルバム一時再生、カート）は、この2つの土台の上に乗る機能なので、先に着手します。
- 見た目の変更のみで依存の少ないもの（アーティスト順ソート＝CR-004、アイコン化＝CR-002）は、構造変更のあとに仕上げとして行います（アイコン化は特に、ミニプレイヤー等の新規UIも対象に含めるため、UIが出そろってからの方が手戻りが少ないと判断）。
- フェーズ番号はplan.mdの続き（フェーズ7〜）としています。

### 実装時に判明した仕様の補正（要確認）
- FR-1.1（フリーワード検索）：仕様では「アルバム名も含めてクライアント側でフィルタ」としていましたが、実装・動作確認の過程で、この絞り込みをそのまま適用するとiTunes Search APIが返す正当な検索結果（曲名・アーティスト名・アルバム名のいずれにも検索語が部分一致しないが、API自身の関連性判定でヒットしたもの）まで誤って除外してしまうことが分かりました。そのため、APIが返した結果をそのまま採用する形に変更し、`acceptance-criteria.md`のFR-1.1もその旨に更新済みです（`matchesFreewordTerm`関数自体は、絞り込み以外の用途に使えるようUnitテスト付きで残しています）。

### Unitテスト
フェーズ7〜11で追加した純粋なロジック（カート・段階検索のURL組み立て・並び替え・アルバム再生順）に対して、Unitテストを新規に27件追加し、既存分と合わせて**全99件が成功**しています（`npm test`で実行可能）。画面（views）・`app.js`は、これまでの方針（plan.md）通りUnitテストの対象外とし、Playwright（この環境に用意されているChromium）を使って実際のブラウザ上で以下を確認しました（iTunes APIへの実通信はサンドボックスのネットワーク制限で行えないため、レスポンスをモックして確認）。
- メドレー作成・詳細画面遷移、検索タブでの追加（追加先選択モーダル→重複判定→追加）
- カートのチェック→カート表示→一括追加（重複はスキップされ、追加できた分だけカートから削除される）
- 段階検索（アーティスト→アルバム→曲）とアルバム全曲一時再生、再生中の画面遷移でのミニプレイヤーの表示・非表示・タップでの復帰
- 無限スクロール（25件→50件ずつの追加読み込み、打ち止めの判定）
- アイコン＋テキストラベル表示、メドレー詳細画面のアーティスト名順ソート
