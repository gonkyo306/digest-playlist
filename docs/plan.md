# 開発計画：お気に入り曲のダイジェスト・プレイリストアプリ

作成日：2026-09-27
根拠：project-charter.md、acceptance-criteria.md、acceptance-test-cases.md
表記：各タスクの括弧内は、対応する受入基準ID（FR/NFR）です。「依存」は、先に終えている必要があるタスクです。
実装言語：素のJavaScript（HTML/CSS/JavaScriptのみ、フレームワーク・ビルド環境は使わない）

## この計画の考え方
- **技術的にリスクが高い部分（画面オフ再生）を最初に検証します。** ここが崩れると、PWAという前提（1-1）自体を見直す必要があるため、他の機能を作り込む前に確かめます。
- 検証後は、**データの流れの下流から上流へ**（保存 → 検索・追加 → 再生）ではなく、**依存関係の少ない土台から積み上げます**（保存の仕組み → 検索 → プレイリスト管理 → 再生 → 仕上げ）。
- 各タスクは、Unitテストを合わせて書く単位にしています。受入テスト（acceptance-test-cases.md）は、Unitテストとは別に、フェーズ5の完了後にまとめて実施します。

```
フェーズ0（技術検証）
   ├─ 実現できず → 人間に相談、方針転換
   └─ 実現できた
        ↓
フェーズ1（データの土台）
        ↓
フェーズ2（検索）      フェーズ3（プレイリスト管理）
        └──────┬───────┘
               ↓
        フェーズ4（再生機能）
               ↓
        フェーズ5（画面仕上げ）
               ↓
        フェーズ6（受入テスト）
```

フェーズ2とフェーズ3は、どちらもフェーズ1（データの土台）にのみ依存するため、並行して進められます。フェーズ4は、フェーズ2・3の両方が完了してから着手します。

## 補足（確認をお願いしたい点）
- フェーズ0で画面オフ再生が実現できなかった場合（0-5）、以降のフェーズは着手できません。この計画は、フェーズ0を通過できることを前提に立てています。
- Unitテストの対象は、ロジック部分（データ処理・判定・状態遷移）に絞っています。画面の見た目や実機依存の動作（画面オフ再生など）は、Unitテストではなく動作確認・受入テストで確かめる想定です。この切り分けでよいか確認してください。

### 実装の補足
- `js/app.js` を、フェーズ0の技術検証用コードから、本番の画面遷移（一覧⇄詳細⇄検索）を扱うエントリポイントに刷新しました。
