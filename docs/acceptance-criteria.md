## 0. 前提・対象範囲

### 対象（今回の受入対象）
- 形式：PWA（1-1）
- 端末：Androidスマホ（Galaxy S26、Android 16、Chrome）（1-2、10-2）
- 回線：Wi-Fi・モバイル回線のどちらでも動作する（測定条件の質問より決定）
- 配信：GitHub PagesでHTTPS公開（10-3、11-1）
- 通信：常にオンライン前提（1-3）

### 対象外（作らない・確認しない）
- 手動での曲順の並べ替え（憲章 決定事項。FR-2.11の自動アーティスト順ソートは対象内）
- プレイリストの複製（3-2）
- クラウド保存・端末間の引き継ぎ・バックアップ（5-1、5-2）
- オフライン再生（1-3）
- ログイン機能（7-1）
- ストア公開、公開時のApple規約確認（7-2：公開を決める段階で実施）
- 英語表示（6-4）
- 今後の再生順・再生済み・経過時間バーの表示（4-6）
- 再生中の再シャッフル操作（4-5）
- iPhone対応（利用者は自分のみ）

### 優先度
- **画面オフ再生は必須要件**とする（NFR-4.5）。PWAで画面オフ・バックグラウンドの連続再生が技術的に難しい場合は、クロスフェード（FR-4.7、2秒）の優先度を下げてでも、画面オフ再生を成立させる。
- クロスフェード付きのまま画面オフ再生が実現できない場合の代替案（優先度順）：
  1. クロスフェードなし（曲間は途切れず切り替わる程度）にして、画面オフ再生を維持する
  2. それでも画面オフ再生が technically 難しい場合は、PWAではなくAndroidネイティブアプリへの切り替えを検討する（1-1の見直し。要相談）
- 最小版の段階で、画面オフ・バックグラウンドでの連続再生を最初に検証する（FR-4.7、FR-4.12、NFR-4.5、第3章）。
- **データ消失**：プレイリストは端末内のみに保存され、バックアップもない（5-1、5-2）。ブラウザの永続保存の要求も行わない（10-1）。ブラウザのデータ削除や、空き容量が少ないときのブラウザの自動削除で、プレイリストが消える可能性がある。許容済みのリスクとして扱う（NFR-3.1、NFR-3.2）。

## 1. 機能要件

### FR-1 曲の検索
| ID | 基準 | 根拠 |
|---|---|---|
| FR-1.1 | 検索画面ではキーワードで検索でき、曲名・アーティスト名・アルバム名のいずれかに一致する曲に加えて、ヒットしたアーティスト・アルバムも同じ結果一覧に含めて表示する（段階検索は廃止し、フリーワード検索に統合）。検索語はiTunes Search APIにそのまま渡し、APIが返す結果（アルバム名の一致を含む）をそのまま採用する。クライアント側で曲名・アーティスト名・アルバム名の部分一致を条件に絞り込むと、APIが返す正当な結果まで除外してしまうことが実装時の動作確認で判明したため、絞り込みは行わない（※実装時に変更） | 2-1、CR-001（アルバム名を対象に追加）、CR-017（アーティスト・アルバムを結果に統合） |

| FR-1.13 | 画面右上の「追加」ボタン（FR-1.12）をタップすると、追加先のプレイリストを選ぶモーダル／画面（FR-2.4）を経て、選択した曲をその場でまとめてプレイリストに追加できる。追加が終わると選択状態は解除される。すでに追加先のプレイリストに含まれている曲は、選択自体ができない（グレーアウト）状態で表示される。重複の判定はFR-2.6に準ずる | CR-008、CR-021 |
| FR-1.14 | アルバム全曲一時再生（FR-1.11）のシャッフル選択は、完全な円形のアイコンボタンのタップで有効／無効を切り替える方式とする。有効なときは、ボタンを強調表示（アクセントカラーで塗る）にして分かるようにする | CR-012、CR-034（ボタン形状を完全な円形に変更） |
| FR-1.15 | アルバムの収録曲一覧画面（FR-1.9）の上部には、Apple Musicのような大きめのジャケット画像（中央寄せ。表示サイズに見合った高解像度の画像を取得する。FR-1.2の検索結果一覧等で使う小さいサムネイルをそのまま拡大表示して粗くしない）→アルバム名・アーティスト名（中央寄せ）→操作ボタン行（完全な円形のシャッフルアイコンボタン＋「再生」という日本語ラベル付きの角丸（ピル型）再生ボタン）を、縦に並べて1回だけ表示する。曲ごとの行は、番号→曲名の順で横並びに表示する（ジャケット・アーティスト名・アルバム名は行ごとには表示しない）。行の上下の余白（padding）は、他の曲一覧（検索結果トップ・プレイリスト詳細）と同じ8pxのままとし、ジャケットが無く番号・曲名の1行だけの内容のため、無理に他の行と高さを揃えず、内容に応じた自然な高さで表示する（強制的な最低高さの指定はしない） | CR-013、CR-034（ヘッダーのレイアウトをApple Music風に変更。ジャケットの高解像度化・行の横並びを明記）。フェーズ22の仕様見直しで行の高さの統一を明記。CR-042：フェーズ23の＋ボタン導入に伴う行の再構成で、行の高さの統一が崩れ、アルバム収録曲一覧の行がプレイリスト詳細の行より高くなっていた（実測：アルバム80px／プレイリスト72px）。**画面モックでの試行錯誤を経て方針確定（2026-09-29、画面モック確認中・未実装）**：他の曲一覧と高さを揃える方式は撤回。余白を4px・6pxに縮める案も試したが、最終的に余白は8pxのまま変更せず、高さを揃えるための強制的な最低高さ指定（CR-034で追加した64px）だけを廃止する方式にした。ジャケットが無い分、自然と他の行より低い、コンパクトな行になる |

### FR-2 プレイリストの管理
| ID | 基準 | 根拠 |
|---|---|---|

## 3. 受入テストの実施条件（案）
- 端末：利用者本人のGalaxy S26（Android 16）、Chrome（最新版）
- 回線：Wi-Fiとモバイル回線の両方
- 曲データ：20曲以上のプレイリストを用意して確認する（NFR-2.1、FR-4.3、FR-4.4）
- 早期確認：画面オフ・バックグラウンドでの連続再生は必須要件（NFR-4.5）。PWAの制約に左右されるため、最小版の段階で最初に検証する。クロスフェード付きで通らない場合は、クロスフェードなしで画面オフ再生が成立するかを確認する
- 曲データ（CR-001〜CR-008分の追加）：検索結果が26件以上になるキーワード（FR-1.10）、アルバムを複数持つアーティスト・複数曲を持つアルバム（FR-1.9、FR-1.11）、アーティスト名が異なる曲を含むプレイリスト（FR-2.11の並び順確認用）を用意する
